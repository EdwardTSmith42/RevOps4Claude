# Models Method — canonical output shape

Use this shape for `modes/models-method`. The mode is an interactive extraction and model-construction process. The final output is a usable visual model plus supporting materials.

Rationale: [one sentence on why this type fits the user's situation — refers to where they're stuck and which model type addresses that]

## Key rules

- **3–4 pillars max.** More dilutes memorability. Hard constraint.
- **Plain language throughout.** No jargon, no buzzwords. A smart non-expert should understand each pillar from its name alone. 7th-grade readability target.
- **Core logic is a belief shift, not a feature list.** If the Core Logic section reads as "this is what our service does," it's wrong. It should read as "here's what you now see / believe that you didn't before."
- **Geometric shape is semantic, not decorative.** Triangle = all required, Circle = cyclical, Venn = intersection is the value, 2×2 = comparison, Line = continuum. Choose based on the relationship, not on aesthetic preference.
- **Explainer script is a skeleton.** Don't produce a 600-word script. A 100–150-word skeleton the user will expand in conversation is more useful than a polished paragraph.
- **Don't force a model type.** If the user's situation doesn't clearly call for Genius / Conversion / Clarity, ask. Forcing a type produces a flat model.
- **The user owns the sketch.** The ASCII sketch is a reference. The real model is drawn by the user, by hand, in real time.

## Grounding check before shipping

1. Is the model type justified by the user's specific stuck-point?
2. Are the pillars distinct, necessary, and describable in plain language?
3. Does the Core Logic express a belief shift, not a feature?
4. Does the explainer script fit in a 7–11 minute walkthrough?
5. Can the user look at this output and actually draw the model themselves?
