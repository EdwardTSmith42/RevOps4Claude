# HFD revops-server API-to-warehouse sync

## Overview

The proven shape (built for the GSC/GA4→Analytics.seo pipeline, PBI 25416): external API → Python export script on **revops-server** → NDJSON staging files → loader → SQL Server `stg` tables → tolerant-load stored procs → `Fact`/`Dim` tables. Verify the whole chain in **Finance_Scratch** under real conditions before any PR. This skill exists because that build caught two silent-failure bugs late (during PR review, not testing) and a follow-on design review caught more before code was even written — the gotchas below are how to not repeat them.

## The checklist

| Gotcha | Why it bites | Fix |
|---|---|---|
| Dev login vs prod login | You develop as an elevated/dev SQL login. The deployed job runs as a **restricted writer login** with no `ALTER`. `TRUNCATE TABLE` needs `ALTER` — ownership chaining doesn't cover it. It works in every test you ran, then fails silently or loudly the first time it runs for real. | Use `DELETE` everywhere staging gets cleared — in the **loader's** pre-bulk-load step AND in every promotion proc. Test the full chain under the actual restricted login, not your dev one, before calling it verified. |
| Proc signature drift | Loader calls a proc with a parameter the proc doesn't declare (e.g. `@LoadBatchId`). SQL Server errors on this in some call styles but silently no-ops (0 rows, exit code 0) in others. | Confirm the exact declared parameter list of every proc against every call site before first deploy, not after. |
| Aggregate reconciliation hides per-source failures | When one job syncs N sources (N forms, N accounts, N sitemaps) in a batch, checking total-rows-loaded across the whole run can mask one source silently returning 0 rows from a bug — indistinguishable from that source legitimately having nothing new that night. | Reconcile **per source**, and know the difference between "0 rows, nothing new" and "0 rows, broken." Alert if a source present in the Dim table is missing from tonight's Fact batch entirely. |
| Partial multi-source runs | A run pulling 54 forms / N accounts can die partway through (rate limit, timeout, network blip) after some sources are cleared/reloaded and others aren't. | Promote atomically per-source, or fail closed (promote nothing) rather than let a partial night's pull silently become "the data." |
| Name-based PII detection has blind spots | Matching sensitive fields by column/question **name** (ssn, dob, routing_number, etc.) misses composite free-text fields ("please provide your SSN, DOB, and account number") and file-upload/signature fields that carry PII without a matching name. | Add a **content-pattern** (regex) second layer on the actual value for high-risk sources, not just name matching. Flag free-text/long-answer fields on sensitive sources for manual review before the first load. |
| Source-side edits break natural-key upserts | If the source system lets a field/question be renamed or re-created after historical records exist, upsert-by-natural-key can silently overwrite or misattribute old data (e.g. a redaction decision made under an old field name doesn't get re-evaluated when the name changes). Compliance-sensitive data (underwriting answers) needs to survive this. | Treat externally-sourced records as append-only/versioned where the source can retroactively change field meaning, not blind upsert-in-place. Log what rule version a redaction decision was evaluated against so drift is detectable. |
| RPC is blocked to revops-server | `schtasks /S`, `Get-WinEvent -ComputerName`, `taskkill /S` all fail with no useful error. | Use WinRM: `Invoke-Command -ComputerName revops-server { ... }`, `Get-CimInstance ... -ComputerName`. |
| The 5AM thundering herd | Multiple scheduled tasks firing at the exact same instant can wedge the physical box in an unkillable kernel I/O hang — only a hardware power-cycle clears it. | Stagger every new trigger time at least 10 minutes from existing jobs; check `C:\Scripts\*` task list first. |
| `.env` BOM | Windows-authored `.env` files often carry a UTF-8 BOM that breaks naive parsers. | Load with `utf-8-sig`, and `setdefault` so a real environment variable always wins over the file. |
| Applocks don't enforce cross-proc ordering | When a tolerant-load proc pair has an FK relationship between their target tables (e.g. a child/fact table FK'd to a parent/dimension table) and each proc takes its own independently-named `sp_getapplock`, those applocks only give re-entrancy protection for the *same* proc — they do nothing to sequence the *pair*. If the child load runs before the parent load has committed a new key, the INSERT throws an FK violation and rolls back the whole batch under `XACT_ABORT ON`. | Document the required call order in both proc headers, and make sure the orchestrator actually enforces it — parent/dimension load must complete before the child/fact load that FKs to it. |
| DBUp deploys by a global numeric key, NOT by folder | The pipeline (`PipelineTemplates/Deploy/dbup-deploy.yml`) flattens all folders and runs each `.sql` in order of `date*10000 + N` (the 2nd hyphen token); folder names are ignored and its `Sort-Object` is unstable. So per-folder numbering (`Table/…-1-…`, `Stored Procedures/…-1-…`, `Views/…-1-…`) produces colliding keys and can run a view before its table → `Invalid object name`. This broke DBUp-Analytics build 66884 (2026-07-09). | Number ALL scripts in a PR as ONE global sequence — unique `N`, ascending in dependency order across folders: tables/stg/indexes/dims → procs → views. Views hard-fail out of order; `CREATE OR ALTER PROCEDURE` survives (deferred resolution). See the `hfd-database` skill's "File Naming Convention & Execution Order". |

## Testing gate before any PR

Build every object (stg/Fact/Dim/procs/views) in **Finance_Scratch** first. Run a real end-to-end pull, not a synthetic sample. Verify: per-source row-count reconciliation, zero raw PII patterns survive where redaction should have applied, idempotent re-run (no dupes), and the load succeeds under the actual restricted production login. Only then open a draft PR (DBUp repo for the objects, RevOps repo for the job folder — mirror the existing job folders like `SeoSync/`). **Note:** a manual Scratch deploy where *you* choose the run order does NOT validate the DBUp script ordering (see the traps table) — separately confirm the filename `N` values are one global, dependency-ordered sequence across folders, or the real pipeline can still deploy them out of order.

## Real-world impact

SEO ETL (PBI 25416): PR review caught the `TRUNCATE`-needs-`ALTER` bug and the parameterless-proc-signature bug — both landed in production code and were only caught by a human reviewer. Fillout sync (PBI TBD): an adversarial design review caught the name-based PII blind spot and the partial-multi-source-run risk **before any code was written**, because this checklist existed to prompt for them.
